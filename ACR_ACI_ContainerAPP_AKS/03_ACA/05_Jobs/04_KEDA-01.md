# ACA Jobs — Event-Driven Jobs with KEDA

Now let's move to the next major topic: **Event-driven Jobs using KEDA**.

This is where Azure Container Apps Jobs become useful for **queue-based and asynchronous batch processing**.

---

## 1. What is an Event-Driven Job?

A **manual Job** starts because you explicitly start it.

A **scheduled Job** starts according to a cron expression.

An **event-driven Job** starts when there is enough work waiting in an external event source.

For example:

```text
             Azure Storage Queue
                    │
              Messages arrive
                    │
                    ▼
                  KEDA
                    │
          Checks queue length
                    │
                    ▼
             ACA Event Job
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       Replica 1 Replica 2 Replica 3
          │         │         │
          ▼         ▼         ▼
       Process    Process    Process
       messages   messages   messages
```

---

# 2. What is KEDA?

**KEDA** stands for:

> **Kubernetes Event-driven Autoscaling**

KEDA is an open-source component that allows workloads to scale based on **events**.

Examples of events:

* Azure Storage Queue messages
* Azure Service Bus messages
* Kafka messages
* RabbitMQ messages
* Redis list length
* HTTP-related event sources
* Many other external event sources

In Azure Container Apps, Microsoft provides KEDA-based event-driven scaling capabilities as part of the platform.

---

# 3. Why do we need KEDA for Jobs?

Consider an application that processes orders.

You have an Azure Service Bus queue:

```text
Orders Queue
-----------------------
Order 101
Order 102
Order 103
Order 104
Order 105
```

Instead of continuously running a container:

```text
Container
   ↓
Keep running
   ↓
Check queue
   ↓
Nothing?
   ↓
Check again
```

an event-driven Job can react to the workload.

Conceptually:

```text
Queue = 0
   ↓
No Job workload

Queue = 10
   ↓
KEDA detects messages
   ↓
Start Job replicas
   ↓
Process messages
   ↓
Job completes
```

This is useful for **batch processing** where the workload is intermittent.

# 4. Simple Real-World Example

Imagine an image-processing system.

Users upload images.

```text
User
 │
 ▼
Application
 │
 ▼
Storage Queue
 │
 ├── image1.jpg
 ├── image2.jpg
 ├── image3.jpg
 └── image4.jpg
          │
          ▼
        KEDA
          │
          ▼
   ACA Event Job
          │
     ┌────┼────┐
     ▼    ▼    ▼
   Job1  Job2  Job3
     │    │    │
     ▼    ▼    ▼
 Process images
```

When there are no images to process:

```text
Queue = 0
```

there is no processing workload.

When messages arrive:

```text
Queue = 100
```

the event-driven mechanism can launch Job work according to the configured scaling parameters.

# 5. Event-Driven Job vs Scheduled Job

| Job Type     | How it starts                         |
| ------------ | ------------------------------------- |
| Manual       | User/application explicitly starts it |
| Scheduled    | Cron schedule                         |
| Event-driven | External event/workload               |

### Manual

```text
User
 ↓
Start Job
 ↓
Execution
```

### Scheduled

```text
Cron
 ↓
Execution
```

### Event-driven

```text
Queue/Event
 ↓
KEDA
 ↓
Job execution
```

# 6. Important ACA Job Concepts

For an event-driven Job, there are several pieces:

```text
Event Source
     ↓
KEDA Scaler
     ↓
Scaling decision
     ↓
ACA Job
     ↓
Replicas
     ↓
Container processing
```

For example:

```text
Azure Service Bus
        ↓
   Message count
        ↓
       KEDA
        ↓
ACA Container Apps Job
        ↓
     Replicas
```

---

# 7. What Does KEDA Actually Do?

Suppose we configure:

```text
queueLength = 10
```

and the queue contains:

```text
50 messages
```

KEDA observes the event source and determines that work is available.

Conceptually:

```text
50 messages
     ↓
   KEDA
     ↓
Need processing capacity
     ↓
ACA creates Job work
```

The exact number of replicas/executions depends on the Job's event-trigger configuration and scaling parameters.

---

# 8. Important Difference: ACA Jobs vs Container Apps Scaling

This distinction is important for your Azure training.

### Normal Container App

A Container App is normally a **long-running application**.

For example:

```text
Frontend API
    ↓
Container App
    ↓
Keep running
    ↓
Receive HTTP requests
```

KEDA can scale the number of application replicas based on events.

### Container Apps Job

A Job is designed for:

```text
Start
 ↓
Do work
 ↓
Finish
 ↓
Exit
```

With an event trigger:

```text
Event
 ↓
Start Job execution
 ↓
Do work
 ↓
Exit
```

So:

> **KEDA provides the event-driven trigger/scaling mechanism, while the Container Apps Job provides the short-lived execution model.**

# 10. What Event Source Should We Use for Our Demo?

For your next practical demo, I recommend **Azure Storage Queue** because the architecture is easy to understand:

```text
Storage Account
      │
      ▼
 Storage Queue
      │
      │ messages
      ▼
    KEDA
      │
      ▼
 ACA Event-Driven Job
      │
      ▼
   Alpine
```

We can keep the actual container extremely simple.

For example, the Job container can run:

```text
echo "Processing queue work"
```

and then:

```text
exit 0
```

This keeps the focus on **KEDA and event-driven execution**, rather than application code.

---

# 11. One Important Point Before the Demo

Unlike our Manual and Scheduled Jobs, an event-driven Job requires an **event source**.

So we'll need something like:

```text
Azure Storage Account
       ↓
Queue
       ↓
Messages
       ↓
KEDA
       ↓
ACA Job
```

We'll also need to configure authentication between ACA/KEDA and the event source. For a production design, **managed identity** is preferable where the supported scaler/authentication configuration allows it, rather than embedding credentials directly.
