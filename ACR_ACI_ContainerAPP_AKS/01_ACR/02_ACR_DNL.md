**ACR Domain Name Label Scope (DNL Scope)** is a security feature in Azure Container Registry that controls **how Azure generates the DNS/login-server name of your registry**.

It is important to understand that **DNL Scope has nothing to do with RBAC, AcrPull, AcrPush, or repository permissions**. It is about the **uniqueness and reuse of the registry's DNS name**. ([Microsoft Learn][1])

# 1. First understand the problem

Normally an ACR looks like:

```text
ACR resource name:
myreg07

Login server:
myreg07.azurecr.io
```

Suppose Company A creates:

```text
myreg07.azurecr.io
```

and uses it everywhere:

```text
Docker
   ↓
myreg07.azurecr.io
   ↓
ACR
```

Later Company A deletes the registry.

Someone else could potentially create a registry using the same registry name and get:

```text
myreg07.azurecr.io
```

This creates a **DNS/subdomain takeover risk** for downstream systems that still trust the old DNS name. Microsoft introduced Domain Name Label protection to address this problem by adding a unique hash to the registry's DNS name. ([Microsoft Learn][1])

---

# 2. Without DNL protection

If DNL is:

```text
Unsecure
```

you get:

```text
Registry name:
myreg07

Login server:
myreg07.azurecr.io
```

If the registry is deleted and the name is later reused, the DNS name can be reused.

Conceptually:

```text
Company A
   │
   ▼
myreg07.azurecr.io
   │
   ▼
ACR-A
```

Delete ACR-A:

```text
ACR-A ❌
```

Later:

```text
Someone else
      │
      ▼
myreg07
      │
      ▼
myreg07.azurecr.io
      │
      ▼
ACR-B
```

That's the problem DNL is designed to prevent.

---

# 3. With DNL protection

Instead of:

```text
myreg07.azurecr.io
```

Azure generates something like:

```text
myreg07-e7ggejfuhzhgedc8.azurecr.io
```

The exact hash is generated by Azure.

So:

```text
Registry resource name
        │
        ▼
     myreg07
        │
        ▼
DNL processing
        │
        ▼
myreg07-e7ggejfuhzhgedc8.azurecr.io
```

The hash makes the DNS name different even if somebody later reuses the registry resource name. ([Microsoft Learn][1])

---

# 4. What does "Scope" mean?

The **scope determines how much Azure allows the DNS name to be reused**.

Current Azure CLI supports:

```text
Unsecure
TenantReuse
SubscriptionReuse
ResourceGroupReuse
NoReuse
```

([Microsoft Learn][2])

Let's understand each.

---

# 5. Unsecure

```text
--dnl-scope Unsecure
```

Login server:

```text
myreg07.azurecr.io
```

No hash.

```text
myreg07
   │
   ▼
myreg07.azurecr.io
```

This is the traditional behavior.

### Security

❌ No DNL protection.

---

# 6. TenantReuse

```text
--dnl-scope TenantReuse
```

Azure generates a hash based on the tenant and registry name.

Example:

```text
myreg07-e7ggejfuhzhgedc8.azurecr.io
```

The idea is that the generated DNS name can be reused under controlled circumstances within the same Microsoft Entra tenant, but a different tenant won't get the same DNS name for the same registry name. ([Microsoft Learn][1])

Think:

```text
Tenant A
 └── myreg07
       ↓
myreg07-HASH-A.azurecr.io


Tenant B
 └── myreg07
       ↓
myreg07-HASH-B.azurecr.io
```

---

# 7. SubscriptionReuse

```text
--dnl-scope SubscriptionReuse
```

The hash incorporates subscription/tenant context.

Conceptually:

```text
Subscription A
      │
      ▼
myreg07
      │
      ▼
myreg07-HASH-A.azurecr.io
```

Another subscription:

```text
Subscription B
      │
      ▼
myreg07
      │
      ▼
myreg07-HASH-B.azurecr.io
```

So the DNS identity is different across subscriptions. ([Microsoft Learn][1])

---

# 8. ResourceGroupReuse

```text
--dnl-scope ResourceGroupReuse
```

The hash incorporates resource-group context as well.

For example:

```text
Subscription 1
│
├── central-in-rg
│     └── myreg07
│           ↓
│     myreg07-HASH-A.azurecr.io
│
└── production-rg
      └── myreg07
            ↓
      myreg07-HASH-B.azurecr.io
```

The DNS names differ because the resource-group context differs. ([Microsoft Learn][1])

---

# 9. NoReuse — strongest protection

```text
--dnl-scope NoReuse
```

Azure generates a unique DNS name every time the registry is created.

For example:

```text
First creation:

myreg07-abc123.azurecr.io
```

Delete it.

Create another registry with the same resource name:

```text
myreg07-xyz789.azurecr.io
```

Different DNS name.

So:

```text
Creation 1
myreg07
   ↓
myreg07-ABC.azurecr.io

DELETE

Creation 2
myreg07
   ↓
myreg07-XYZ.azurecr.io
```

This gives the strongest protection against DNS-name reuse. ([Microsoft Learn][1])

---

# 10. Visual comparison

| DNL Scope              | Login Server              | DNS Reuse Scope                    |
| ---------------------- | ------------------------- | ---------------------------------- |
| **Unsecure**           | `myreg07.azurecr.io`      | No DNL protection                  |
| **TenantReuse**        | `myreg07-HASH.azurecr.io` | Reuse within tenant                |
| **SubscriptionReuse**  | `myreg07-HASH.azurecr.io` | Reuse within subscription          |
| **ResourceGroupReuse** | `myreg07-HASH.azurecr.io` | Reuse within resource group        |
| **NoReuse**            | `myreg07-HASH.azurecr.io` | Never reuse generated DNS identity |

The exact hash format/value is generated by Azure. ([Microsoft Learn][1])

# 11. Let's create one using CLI

For example:

```bash
az acr create \
  --resource-group central-in-rg \
  --name mysecureacr123 \
  --location centralindia \
  --sku Standard \
  --dnl-scope NoReuse
```

Then:

```bash
az acr show \
  --name mysecureacr123 \
  --query "{name:name,loginServer:loginServer,scope:autoGeneratedDomainNameLabelScope}" \
  -o json
```

You might see something conceptually like:

```json
{
  "name": "mysecureacr123",
  "loginServer": "mysecureacr123-abc123.azurecr.io",
  "scope": "NoReuse"
}
```

---

# 12. Important impact on Docker

This is where DNL becomes very practical.

Without DNL:

```bash
docker tag myapp myreg07.azurecr.io/myapp:v1
```

With DNL:

```bash
docker tag myapp mysecureacr123-abc123.azurecr.io/myapp:v1
```

So your **login server is no longer necessarily identical to your ACR resource name**. Microsoft explicitly notes that downstream Dockerfiles, Kubernetes YAML, Helm charts, and other references need to use the full DNL-protected login server. ([Microsoft Learn][1])

---

# 13. Important impact on ACI

Suppose you have:

```text
ACR resource:
mysecureacr123
```

but the login server is:

```text
mysecureacr123-abc123.azurecr.io
```

Your ACI image must use:

```text
mysecureacr123-abc123.azurecr.io/mynginx:v1
```

NOT:

```text
mysecureacr123.azurecr.io/mynginx:v1
```

For example:

```bash
az container create \
  --resource-group central-in-rg \
  --name mycontainer \
  --image mysecureacr123-abc123.azurecr.io/mynginx:v1 \
  ...
```

This is a common source of confusion when students first see DNL.

---

# 14. How to get the actual login server

Never manually construct it.

Run:

```bash
az acr show \
  --name mysecureacr123 \
  --query loginServer \
  -o tsv
```

You might get:

```text
mysecureacr123-abc123.azurecr.io
```

Use that value.

You can also get the DNL scope:

```bash
az acr show \
  --name mysecureacr123 \
  --query autoGeneratedDomainNameLabelScope \
  -o tsv
```

# 15. DNL is NOT an access-control feature

This is extremely important for your AZ-104/Azure course.

Don't confuse:

### Domain Name Label Scope

```text
DNL
 │
 └── DNS name uniqueness/reuse
```

with:

### RBAC

```text
RBAC
 │
 └── Who can access ACR
```

or:

### ABAC

```text
ABAC
 │
 └── Which repositories the identity can access
```

So:

```text
                 ACR
                  │
       ┌──────────┼──────────┐
       │          │          │
       ▼          ▼          ▼
      DNL       RBAC       ABAC
       │          │          │
       │          │          └── Repository access
       │          └───────────── Who can do what
       └──────────────────────── DNS name protection
```

This distinction is very important.

# 16. Your `myreg07` example

Your current registry is:

```text
myreg07
```

You've been using:

```text
myreg07.azurecr.io
```

That indicates you're working with an **Unsecure-style login server**, i.e. no DNL hash in the login server.

If you create another registry with:

```bash
--dnl-scope NoReuse
```

you might instead get:

```text
mynewacr-xxxxxxxx.azurecr.io
```

Then your complete flow becomes:

```text
Docker
   │
   │ push
   ▼
mynewacr-xxxxxxxx.azurecr.io
   │
   ▼
ACR
   │
   │ pull
   ▼
ACI
```

## Interview answer

If an interviewer asks:

**"What is Domain Name Label Scope in Azure Container Registry?"**

A good answer is:

> **Domain Name Label Scope is an ACR security feature that controls how Azure generates and reuses the registry's DNS/login-server name. DNL can append a unique hash to the registry's login server to protect against DNS/subdomain takeover when a registry is deleted and its name is later reused. The scope determines the boundary for DNS-name reuse, such as tenant, subscription, resource group, or no reuse. It is unrelated to RBAC or repository permissions.** ([Microsoft Learn][1])

### One thing to remember

```text
DNL = Protect the NAME
RBAC = Protect the ACCESS
ABAC = Protect the REPOSITORY
```

That is probably the easiest way to remember the three concepts.
